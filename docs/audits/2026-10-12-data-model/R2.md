## 2. `metric` effects credited to their senders

`MetricDeltas` is `Partial<Record<DeltaMetricKey, number>> & { approval?: never }`. A `Record`'s keys have no declarations, so the walk never saw a sender. It credited only `applyMetric`, through its merge loop. Now:

- A key written into a type aliased `MetricDeltas` maps onto `MetricSet` by name (`PAYLOAD_ALIASES` in `scripts/lib/metric-sites.mjs`). This happens in the engine and content packages only, because in player-core and the web app a `MetricDeltas` is a price restated for the player.
- `applyMetric` is a named payload handler (`PAYLOAD_HANDLERS`, listed under `handlers` in the report) and is no longer credited.
- A narrower patch spread into a payload (`{ ...UNILATERAL_FORCE_COST }`) counts as its keys.
- 77 declarations now write a `MetricSet` field: senders, cost tables (`PRESS_PLAYS`, `EXECUTIVE_ORDERS`, `STRUCK_DOWN_COST` and others) and the founding metric builders.
- 20 sites hand an effect a whole `MetricDeltas` (`deltas: projection.cost`, `deltas: actCost(...)`). The walk cannot tell which keys those send, so they are named blind sites under a ratchet.

## 3. Computed keys

`policy-program.ts#statEffect` and `order-lineage.ts#ownerWeight` both build `{ [group]: { [field]: next } }`. The walk now resolves a patch with computed keys from the dotted paths in scope: parameters, locals and destructured bindings typed as a union of dotted string literals (`PolicyStatPath`). It credits every field the union names, with the note `(computed key over T)`. A computed patch with no such path in scope is a named blind site. There are none today, and a new one fails the gate.

## 4. Scenario gates

`content/corpus/` is gitignored. The corpus the player is dealt is the 17 authored packs, the 7 pilot scenarios and the 322 baked scenarios in `packages/player-core/src/content/bundled-corpus.generated.ts`, 346 in total. `scripts/lib/content-gates.mjs` reads them from `dist/` and counts, per field, the scenarios whose conditions or `band` cast gate on it (`contentGates`). 18 fields are gated on today. The condition table names its evaluator for every row, and the gate fails when the walk does not see that evaluator reading the field. Condition kinds that read no registered field are listed with what they read instead (`relationship`, `alignment`, `flag` and others). A kind in neither list fails.

## 5. The gate's failure modes

| Finding | Since | Proof fixture (planted) |
|---|---|---|
| `UNREGISTERED`, `UNDECLARED`, `NO READER`, `STALE REPORT`, claimed-reader `NEW`/`STALE`/`RAISED` | R1 | unchanged |
| `NO WRITER`, which now needs a writer outside the dataset and founding | R2 | an effect-written field only the dataset writes; a metric field only the handler touches; a field whose only writer is a computed patch, with the path removed |
| `FOUNDING WRITTEN` | R2 | a founding-only field a campaign writes (the same field written by the dataset passes) |
| `GATE UNREAD`, `GATE UNREGISTERED` | R2 | a gate whose table row names an evaluator that does not read the field |
| `GATE UNCLASSIFIED` | R2 | a scenario gated on an unknown kind |
| blind sites `NEW opaque` / `NEW computed` (ratchet, replacing R1's outright `OPAQUE`) | R2 | an effect payload typed as the whole patch; a computed-key patch with no path in scope; the same payload forgiven by the baseline passes |

The clean fixtures prove that a metric write is credited to its sender rather than the handler, that a computed patch resolves from its path, and that a gate read through its named evaluator passes.
