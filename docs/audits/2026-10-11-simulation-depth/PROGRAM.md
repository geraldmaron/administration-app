### Presidential decision and processing contract

One shared local flow, adapted to the action's institution, replaces inconsistent single-click finishes:

1. **Select and compare:** player chooses an option against the baseline and sees target, authority, cost, risks, forecast and deadline. Selection is not commitment.
2. **Open presidential review:** a focused overlay shows the exact chosen act/targets/recipients, current terms and irreversibility. Context remains recognizable behind it. Run a stylized identity/biometric scan and body-temperature readout as an explicitly simulated presidential authorization sequence. Use local SVG/CSS/canvas or bundled assets; no camera, microphone, sensor API, credential prompt or remote generation. Fictional scan values cannot affect eligibility, odds or engine state.
3. **Confirm deliberately:** offer a clearly named final action (for example “Confirm and sign”) and Cancel/Return to terms. A second distinct activation is mandatory; neither scan completion, Enter carried over from opening, animation end nor timeout commits. Do not require holding a key as the only accessible path. A reduced/skip-animation option still requires explicit confirmation. Revalidate the captured campaign/terms before the existing commit boundary; if changed, explain the changes and require fresh confirmation.
4. **Resolve with visible activity:** show a task-specific stage view and a bounded, readable log. Real evaluation/recorded-event progress is preferred. Congressional voting can reveal each recorded member name and vote, tally and procedure threshold; show party/caucus only as permitted. A formula view may show actual player-safe inputs, weights and result where the model exposes them; label unavailable/private inputs, never disclose hidden allegiance or fabricate arithmetic. A bill submission must show “Sent to committee,” not calculate a final roll call before the simulation reaches that vote. Court independent deliberation remains independent. Intelligence collection takes its actual game time; the overlay must not imply instant completed surveillance.
5. **Publish the result:** after the authoritative result is available, update the relevant bill/case/order/report/Record surface, highlight what changed and offer a direct destination plus dated receipt. Preserve the existing event IDs and original actor. Refusal gets its own outcome; success is not displayed before an act applies. Save failure says “applied, not saved” and exposes save-only recovery.

**Timing and truth:** separate actual compute progress from a paced replay of already-computed results. If computation completes immediately, label the animation as reviewing/tallying the recorded result, not as work still running. No fabricated percent, fake computational stall, artificial minimum wait or one delay per all 535 members. Batch/virtualize the log; offer skip-to-result and details after completion. The ceremony is immersive but must not worsen the owner's latency complaint. Display can be dismissed after commit while work safely completes; dismissal is not rollback. Cancel before commit changes nothing. Single-flight guards, exactly-once application, stale checks, snapshot forecasts, deterministic RNG and privacy remain intact. Refresh/crash recovery uses persisted campaign truth; never silently resubmit an action from UI state.

Navigation/filter/theme changes need no presidential ceremony. Destructive save management keeps a concise, specific confirmation appropriate to that utility.

**Local processing architecture:** source inspection shows projection workers already report progress, while Continue currently calls the store with only a busy/status presentation. Determine whether the relevant resolver yields before designing a live log. If a synchronous computation blocks paint, profile first, then use a local worker or bounded yielding with deterministic ordering if justified.
